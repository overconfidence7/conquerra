## Practical notes (learned the hard way)
- **Secrets never touch the chat or a file in the repo.** The VAPID private key, `REPORTS_TO`, and from 36 the session secret and the Google client secret are set with `wrangler secret put` on Nate's computer, from a generated value or by Nate typing it; the session never prints one, and you never ask Nate to paste one into chat.
- Caching can poison a deploy: a path answered with the wrong body under a long cache header stays wrong at the edge, in the browser and in the service worker's precache. Any new static path gets the right status and a cache header that matches its body. When a page is blank, read the console first. The service worker can pin a tab to an old build (35): clear the offline cache.
- One account can test most of online, but not two people's live updates, a group chat's secrecy, a block seen from the other side or a push to a second device: the sessions test those with two accounts against `wrangler dev` and the harness (`apps/web/scripts/table-harness.mjs`, `big-table-harness.mjs`, `s34-kit.mjs`), and the test lists mark what waits for a friend.
- Usage limits. Nate's plan has usage windows. Keep sessions to about four or five parts in priority order, each ending with commit and push, and tell the session to stop cleanly at a part boundary if it's running low. Nate prefers one whole session per usage window; long sims run in the background on his machine (19 workers).
- Run Claude Code locally, never in the cloud, for anything touching art, sound, the browser, Cloudflare, secrets or deploys.
- Two Claude sessions on Nate's computer at once share his usage window and can clash over files.
- Your docs must reach GitHub before a session starts: commit to `main` with the attribution lines and push. The session's Step 0 pulls. Don't push docs while a Claude Code session is open on Nate's computer (check his folder: `git --no-optional-locks status`, no `.git/*.lock`), unless you're happy to rebase. When Nate brings you play-test notes, record them yourself.
- Git on Nate's computer: `git --no-optional-locks …` for read-only commands. The device shell is a Linux VM with Nate's folder mounted; it can't reach the internet. Never run `pnpm install` there.
- The server: the AUD tag is a Wrangler variable (read-only, until 36 retires Access); friends' emails go into the Access policy "Conquerra players" (Nate's step, until 36); `pnpm deploy:preview` applies D1 migrations, Workers Builds doesn't. The lock check (`pnpm check:preview`) covers the API and a real WebSocket; after 36 it checks the cookie, not Access.
- A session that plays test games on the preview plays as Nate (his sign-in), and they land in his list. Ask the session to resign and leave them; the daily cap of 20 tables is also the load test's budget.
- The Free plan's limits (checked Oct 13): 10 ms of CPU per request on the Worker's handlers, 30 s per request in a Durable Object, 100,000 requests and 13,000 GB-s of room time a day, 5 GB of storage. Errors 1102 (CPU) and 1027 (requests) show in `wrangler tail`. Workers Paid (36) lifts the handlers to 30 s and opens Email Sending to anyone.
- Art batches are made by a separate Claude chat that drives Gemini (`docs/prompts/gemini-art-session-04.md` is the latest template). The art-list test counts file names under "## Batch 3" onward: never write that literal heading elsewhere; run `pnpm vitest run packages/art` after every edit to the art list.
- Sound: every file's source, author, license and date live in `packages/sound/data/credits.json` (the test refuses anything not CC0 / public domain / CC BY); check every new source's page yourself.
- Screenshot scripts stage views, so a shot can look inconsistent without a real bug; ask the session to check in a real game before calling it a bug. But do read everything in the shot.
- Random-input (property) tests find real problems but can fail on an unrelated commit. Reproduce the case before deciding. Pinned "fingerprint" tests change whenever behaviour changes: a session must re-pin in the same commit.
- A "no difference" sim result needs a reason: when a script forks workers, check the flag under test reaches them (32). When two settings give identical games, prove the setting was applied before trusting it.
- **A balance number needs the right count:** 300 games can't tell two settings apart by seat; a by-spot share needs fresh games (the search's games and the proof's games differ); a dealt personality needs 2,700 games a fog and a second seed (34b); the bar is read beside the noise, "on average" beside "furthest".
- A leak can be on the page alone: the wire clean, the bots honest, and the drawing or the words still showing a person more than they should (an outline through the cloud, a boat on a lane never seen). Read the screen.
- Planning-time and build-time numbers depend on the machine that day, and on the extension's debugger in your Chrome tab (four times slower); only side-by-side runs on one machine mean anything.
- **A fixed test-worker count breaks CI:** GitHub's runner has 2 cores; `maxWorkers` must follow the core count. A test that runs past a minute without yielding trips vitest's worker call on a busy machine: split it.
